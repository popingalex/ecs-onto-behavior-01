## 2. 不可变更的领域约束（全部修改必须遵守）

### 2.1 回合和 System 读写语义

1. 各 System 默认读取同一不可变 `State[n]`。`read_previous` 永远取 `State[n]`。
2. 一个执行上下文的 `read/read_self` 可优先读取**自身**私有暂存；其他 System 的暂存不可见。并行实体分片也不能任意窥视彼此暂存。
3. `order` 边只改变调度先后，不隐式产生新状态可见性；`effect` 边收集效果；`product` 边未实现时必须拒绝。
4. 请求（requested）≠获准（approved）≠最终提交（final）。归约/裁决需遵循确定且可解释的版本化规则。
5. 本回合有效结果、运行记录、来源边、状态增量和分支 head 要在逻辑上**原子提交**，出错不改变 head。
6. 旧世界、节点私有预览、候选结果、获准结果、最终状态要有独立且明确的 UI 标识。
7. 序列/逻辑顺序不等于现实因果；来源图记录执行依据，反事实须分支重算。

### 2.2 ECS 对象、值和图文档

- 实体类型、组件定义、属性定义、实体模板、实体实例、运行属性值是不同对象。修改定义不能静默改历史记录。
- `null`（显式清空）、不存在 override（恢复继承）、不适用（未装配组件）、未知来源、数字 `0` 和合法原点坐标彼此不同。
- 属性单位要区分绝对温度 °C 与温差 K；绝对温度不能直接连到温差贡献端口。
- P12 外层 `ScheduleDocument` 与 P14 内层 `LogicGraphDocument` 的 schema、节点注册表、撤销历史、保存版本独立。
- 移动画布节点、缩放及布局变化不应改变语义哈希；程序内容、参数、绑定、约束改变则应使校验/发布状态过期。
- 已发布 bundle、运行时程序快照和历史属性版本不可被当前草稿覆盖。
- 无位置的逻辑实体仍可参与计算；位置 `[0,0,0]` 是有效空间值。

1. P29 新增一个不同于种子数据的属性定义，设置量种/单位/nullable/约束；
2. P03 将其加入组件，P02 类型与 P05 模板正确引用；
3. P08 新建实体或应用模板覆盖，保存并刷新；
4. P10 查询结果随实体有效类型和组件装配而变化；
5. P15 变量候选从 schema 和作用域动态出现，而不是固定候选数组；
6. P14 图引用新的有效 binding 后可保存、校验；P11/P12 引用正确版本；
7. P20 执行结果确实由**当前图和世界状态**产生；
8. P22–P24 显示正确版本来源；删除被引用对象受阻。

若当前五节点执行器不能支持新属性的通用运算，须**正确拒绝不支持的算子**，并至少验证新实体进入 q-fire / 已支持冷却程序的动态查询；不为了通过测试而扩大虚假功能范围。

### W2.4 尺寸、焦点和交互故障

浏览器至少验证 `1440×900` 和 `1920×1200`：

- P12/P14/P20/P22/P26/P31 关键工具、表单、错误提示、抽屉、弹层可见且可操作；
- P20 工具栏不横向溢出，滚动或聚焦不会造成视觉重叠；
- 画布拖放/连线/框选、撤销重做、文档切换、刷新恢复正常；
- 键盘与焦点状态不因 overlay 关闭误触另一页面的快捷键；
- 空态、失败态、加载中、历史只读、未保存、已保存、已发布有可辨识的表现。

### W2.5 页面完成度的新统计口径

建立 `page-capability-matrix.md`，**不再使用“无 Placeholder”代替业务完成**：

- A：可编辑并已业务验收；
- B：只读/诊断/回看，且确有真实数据；
- C：外部模块迁移或导航说明；
- D：明确受契约限制而不可操作；
- E：缺失、无法进入或仅装饰性外壳（v0.6 不允许核心页有 E）。

记录每页实际角色、数据源、交互、保存对象、权限状态、回归证据与后续责任模块。

## 7. W3 — 不可变执行记录、单位和属性来源（P0）

### W3.1 固定追溯必备字段

检查并在现有 DTO/存储中**补缺**（不要因为本文列出的英文名称不同就另造第二套模型）：

| 记录 | 最少需要能关联的信息 |
|---|---|
| Run / Commit | `runId`, `branchId`, `baseCommit`, `resultCommit`, `modelBundleId/hash`, `scheduleVersion/hash`, 模拟时间与输入 |
| SystemExecution | `systemId/version`, `queryId/version`, `programId/version`, entity batch、执行顺序、读取状态/上下文 |
| NodeExecution | `nodeId`, 实际输入/输出、单位/量种、`inputVersionRefs`, 顺序、完成/跳过/错误 |
| EffectRequest | 请求 effectId、来源 execution/node、目标属性、请求量与单位 |
| ConstraintDecision | decisionId、约束/归约规则版本、group、获准/拒绝/部分、比例/额度与理由 |
| PropertyChange | 对象/属性稳定 ID、前后属性版本和值、提交 ID、effect/decision 来源 |
| Graph/Schema snapshot | 运行当时的节点/端口/绑定、schema 与单位定义，可由不可变 bundle 引用 |
| DependencyEdge | 从实际读取版本到实际执行/决策/输出的可查找边 |

必须区分**实际读取依赖**与为调度声明的可能读写集合。记录为零净变化时，如确有两路抵消贡献，不能因最终值没变就丢掉执行与请求事实。

### W3.2 历史图不可变

测试步骤：

1. 用程序 `g@v1` 执行并保存 run R1；
2. 修改参数或节点结构，形成 `g@v2` 并执行 R2；
3. 进入 R1 的 P22：显示旧图/旧参数/旧 binding/旧端口单位；P23 裁决和 P24 输入版本不受 R2 或当前草稿影响；
4. 回到当前图编辑器，不能意外改写 R1；
5. 切换 branch/viewCommit 后仍稳定解析 R1。

### W3.3 P22 单位与近似回落治理

报告描述 P22 优先用记录图快照读取端口单位，仍存在启发式回退（`≈` 标记）。整改要求：

- 优先历史 `schemaVersion` / `graphSnapshot` / 端口记录的明确单位；
- 如果老记录信息缺失，显示“来源不完整 / 无法验证单位”；可在**展示提示层**给 `≈` 推测，但不能将推测写回权威 trace 或当作可审计真实单位；
- 新版本正式提交的记录若按契约必须含单位却缺失：进入验证失败/不完整状态，不得静默拿当前 schema 回填；
- 记录“推测依据”与“事实来源”两个不同字段或显示层状态。

### W3.4 值语义和缺值

新增回归：`0`、`false`、`null`、未装配、未知来源、未裁决 pending、有效位置 `[0,0,0]`；P27 分支对比不得把缺值当零，P24 不得用最新世界值补老版本的缺失输入。

### W3.5 审计失败用例

- 缺失一个 `inputVersionRef`：页面指出具体不可完整追溯的节点；不编造边。
- 旧 schema 与新 schema 单位不同：历史保持旧值与旧单位，不重新解释数字。
- 图布局改变但语义不变：哈希与结果不变；节点运算或 binding 改变：校验过期、发布版本变化。
- P18 发布 bundle 不可变；run 必须引用固定版本，不引用可变化的草稿对象。

## 8. W4 — 本地运行历史持久化（P1，作为 v0.6 发布门槛）

### W4.1 设计目标与非目标

报告明确说：**计算提交保存在会话内存，刷新后消失。**这对以历史/分支为核心的产品是明显的下一步缺口。

本轮建议采用浏览器 **IndexedDB 或复用仓库现有的事务化本地存储层**；如果已有可靠实现应优先复用。原因是 commit、trace 和多分支记录可能大于简单配置草稿，不能以单个同步 `localStorage` 巨型 JSON 作为长期默认实现。此为**新实施建议**，不是声称仓库已选定 IndexedDB。

范围只包含本地浏览器原型级事实恢复，不包含生产多端一致性、PG 服务权威事务、Rust 内核检查点、插件内部状态恢复或自动跨设备共享。

### W4.2 最小持久对象和事务

每次成功提交必须能恢复：

- 已发布/运行引用的模型、场景、程序、System、Schedule 版本或不可变 bundle；
- `Commit`（父节点、branch、模拟时间、base/result、版本引用）；
- 状态快照或可恢复的基准快照＋有序属性增量；
- `RunRecord / NodeExecution / EffectRequest / Decision / PropertyChange / Dependency`；
- 分支元数据、branch head、独立 `viewCommit`（viewCommit 可按 UI 用户设置保存，不得等同于 head）；
- schema/数据格式版本、迁移元数据、完整性校验。

**原子性建议：**在同一存储事务内写入当次事实及新的 branch head；写失败时仍指向旧 head，恢复时不得暴露半提交的历史。若本地存储能力不足，发布前必须明确采用何种可验证的两阶段暂存/commit marker 方案，不能口头承诺“原子”。

### W4.3 必须验证的恢复路径

1. 运行基线 R1，刷新：R1 的 commit/trace/分支仍存在，P22–P27 可回看；
2. 修改参数运行 R2，刷新：R1/R2 的图快照和结果均各自保持；
3. 从 R1 建分支 B，分支 B 续算 R3，刷新：A/B 的 head、共同祖先和差异正确；
4. 在历史 commit 仅“查看”不应移动共享分支 head；
5. 人工模拟存储写失败/配额不足/版本迁移错误：旧 head 保持，界面显示失败与可恢复动作；
6. 冷启动导入/导出当前场景与历史包（如本轮不支持导入，必须在 UI 和验收记录明确，而不是把“刷新可恢复”写成“任意设备可迁移”）。

### W4.4 一致性与迁移

- 定义 `historySchemaVersion`、持久化键空间及升级/回滚策略；
- `documentId` 草稿持久化与 commit 历史持久化相互隔离，不能混用同一 undo；
- 记录对模型 bundle 的固定引用；bundle 丢失时禁止悄悄套用最新模型；
- 恢复后核对 branch head、父链接、属性版本与实际世界快照的一致性；
- 若 seed 每次启动自动加载，须明确“首次初始化”和“已有本地世界恢复”，避免覆盖用户数据；
- 大量 trace 按 run / entity / node 分页加载；本轮至少建立可衡量的体积与响应基线。

**明确限制：**能加载历史状态不自动证明“从任意历史中间点完整恢复任务/RNG/插件后重新推演”。该能力属于 v0.7 以后的正式 checkpoint/adapter 范围。

## 10. W6 — MapEngine / Rust-WASM 的集成契约准备（P1 文档任务）

### W6.1 MapEngine 接口（v0.6 只定义，不接入）

必须由本仓库与 mas-suite MapEngine 的责任人审定以下契约：

| 契约项 | 必须澄清的内容 | 必测情况 |
|---|---|---|
| 稳定身份 | `projectId`, `sceneId`, `entityId`, `assetId`、模板和版本标识 | 重命名不换 ID、删除引用受阻 |
| 场景数据 | 世界实体模型 vs MapEngine 空间表现/装配数据的所有权 | 逻辑实体无位置也存在 |
| 坐标 | 坐标系、坐标轴、原点 `[0,0,0]`、null、单位、高程基准 | 原点有效、null 不显示 |
| 版本 | `sceneVersion`, `modelBundleId`, `commitId`, `branchId` 的映射 | 切历史时空间表现匹配 |
| 选择联动 | ECS 表格选中→地图聚焦；地图选中→实体检查器 | 无空间表现实体不能误丢失 |
| 运动权威 | 轨迹、路线版本、位置/速度与到达事件由谁产生 | 不允许客户端视觉路线改变业务事实 |
| 资产 | 3D asset id、离线地址、版本、缺失处理 | 资源失效不写假坐标 |
| 错误/能力协商 | 模块未安装、版本不兼容、无法加载、只读状态 | 降级解释明确，不假装集成成功 |

建议产物：`design/03/contracts/mapengine-integration.md`、独立 fixture 和契约测试规范。P06/P07/P09 在接入前是**迁移/入口页**，不能计作本仓库完成了场景装配、地图和模型库。

### W6.2 `ExecutionAdapter` / Rust-WASM 适配契约

正式执行器应与参考 TS executor 对齐的**输入**：

- 固定 model/schema bundle、场景 baseWorld/commit、graph/schedule/system/query 的确定版本；
- 参数、回合命令与幂等键、模拟步长、策略/随机源引用；
- 版本化执行/归约/单位语义；不直接拿“当前 UI 表单状态”作为隐藏输入。

**输出**对齐：

- 成功：nextWorld、RunRecord、System/Node Execution、Effects/Decisions、Changes、Dependencies、diagnostics；
- 失败：结构化错误和明确失败边界，不更新 head；
- 容许 UI 提供播放事件/时序，但动画只是已提交结果的投影，不重新决定状态。

先做**语义对照测试**：TS 参考器与 Rust/WASM 对相同输入输出的领域结果、请求和来源结构一致；浮点容差要按算子/量种明示，不能用不受控线程顺序或隐式四舍五入掩盖错误。随后才推进性能、并行、WASM Worker、原生客户端复用和 checkpoint 验证。

### W6.3 决策记录

产出 `architecture-decisions.md`，明确：

- React/Figma Make 是当前原型 UI 技术选择，**不取消**长期 Rust 共享推演内核及原生/WASM 客户端目标；
- TS executor 是参考器、调试器与一致性对照来源，不应被包装为最终生产计算核心；
- MapEngine 是独立模块时，数据/身份/版本边界需先确立；
- PG/SQLite/持久服务等属于未来正式数据层，不因 v0.6 使用 IndexedDB 被排除。

## 12. 推荐的验收执行脚本（手工/E2E 均可参照）

### 12.1 标准纵向旅程 J1：编辑→运行→追溯

1. 冷启动应用，确认种子 F01/F02/F03、A/B 与正确程序引用。
2. P02/P03/P29/P05/P08 校对对象关系和默认/覆盖含义；至少实际修改并保存一个非关键字段再刷新。
3. P14 查看内部五节点与必需边；P15 验证 binding；返回 P12 检查外层四节点类型和 edge。
4. P20 执行**当前图**，保存 R1 commit；查看外层批次、System/实体矩阵。
5. 在 P22 查看 F01 的 A/B 读取、节点输出；P23 核对 −50/−50、0.8、−40/−40；P24 追至输入属性版本。
6. 回 P12 添加 A→B 的 order 边，运行 R2；B 仍读 100°C，结果不因顺序边变更。
7. 回 P11 停用 B，运行 R3，得到 50/30/20°C；再启用 B、将 A 改 20K，运行 R4，得到 30/20/20°C。
8. 删除 P14 必需连接并试运行，应被拒绝且 head 不动；恢复连接。
9. 刷新，R1–R4（及失败诊断按产品定义可选）仍可查询；旧运行使用固定图快照。
10. 从旧 commit 建分支 B，改变参数续算；切分支，P26/P27 头与差异正确。

### 12.2 反向旅程 J2：从结果追至来源

P27 的两分支差异 → 某个属性版本 → P24 输入版本 → P23 约束/额度/获准 → P22 具体 System/实体/节点和历史 program → 原模型/属性 schema 版本。**每次跨页必须保留并显示 branch、commit、run、execution/entity/node ID**；找不到旧版本时应明确报告缺失，不落到当前最新值。

### 12.3 失败旅程 J3：拒绝、错误、恢复

无效单位 → 拒绝连线/校验；断必需端口 → `INPUT_MISSING` 无提交；成环 → 拒绝执行；存储失败 → 旧 head 保持；程序版本缺失 → 历史显示“不完整”而不是借当前程序解释；MapEngine 未连接 → 显示迁移/未连接，不画假地图。
