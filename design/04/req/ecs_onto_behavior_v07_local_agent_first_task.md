# 本地 Agent 首轮任务：双工程只读审计与 v0.7 集成可行性报告

> 任务状态：待用户在本地提供两套工程根目录  
> 工作台：`ecs-onto-behavior-01`（报告基线 `ee2070e`，需验证实际 HEAD）  
> 原有推演系统：`<USER_PROVIDED_ENGINE_ROOT>`  
> 第一轮性质：**只读审计，不修改源码、不升级依赖、不初始化或清理真实数据库、不提交/推送、不运行可能改变业务世界的命令**

## 任务目标

为 `ecs-onto-behavior-01` 和现有推演系统设计**最小可实现的真实数据集成路径**。当前工作台的角色是：
- ECS/本体可视化编辑器；
- System 外层调度和内部程序可视化编辑器；
- 真实推演结果、来源和历史分析工具；
- 地图/场景模块的集成宿主。

现有 TS mock executor 是参考器，不是要替换原系统的正式计算内核。

## 第一步：确定工程事实

1. 核对两个根目录、AGENTS.md/README/项目文档、当前 SHA、工作区差异、入口/构建配置和可运行样例。
2. 只读定位：ECS/属性 schema、模板/实例、查询、System 注册和调度、数值/矩阵计算、任务/事件、执行结果、trace/来源、历史/分支/快照、GIS/MapEngine、API 和存储。
3. 对工作台定位：`ExecutionAdapter`/TS mock、`draftRegistry`、IndexedDB、P02/P03/P05/P08/P29、P10/P11/P12/P14/P15、P18/P19/P20/P22-P27、`MapViewport`、单测和验收材料。
4. 对每项能力写**实际文件路径/关键符号/源码行区间/测试证据**。不许凭说明文字判断已实现，也不许因为搜索不到就断言不存在；扩展实际调用链核查。
5. 真实工程的技术栈、身份体系、执行语义和存储能力都必须从源码核查，不直接套用旧的 JS/Cesium/Java/Rust 讨论。

## 第二步：列出语义映射与差异

建立双工程能力矩阵，列：
`对象/能力 | 工作台实现 | 原系统实现 | 可映射等级 | 语义冲突 | 预计最小改动 | 证据 | 方案`。

至少覆盖：
- ID/实体类型/组件/属性/关系与矩阵块；
- 原始值、默认/继承、显式 null/未装配/0、单位/量种/位置；
- System 顺序/依赖/并行、State[n]、私有暂存、效果和归约/提交；
- 动态 System/程序注册、参数、脚本/算子、可视化编译；
- run/system/entity/node/实际输入版本/变更/裁决记录；
- 按 commit 的历史回放、分支、恢复续算、RNG/任务等状态；
- 地图资产/位置/路线权威及切分支联动。

明确 S0（原生黑盒 System）、S1（参数/规则可映射）、S2（内部图可编译）三类，**不要默认所有 System 都能转 FlowGram 图**。

## 第三步：选择真实只读样例

从已有系统**真实存在**的业务样例里选择一个足够小、可复现的场景，优先具备：
- 多种类型/组件/属性和一些关系；
- 至少两个 System 或一次可观察的规则演化；
- 一次真实运行的输入和结果；
- 尽可能具有历史/日志/来源；
- 可以脱敏复制到隔离测试目录，不暴露业务秘密。

如果没有现成可导出数据，不要造替身场景冒充；列出导出数据所需最小只读探针或导出器改动方案。

必须记录来源系统完整版本、fixture 版本/校验和以及授权数据使用范围。

## 第四步：生成集成方案，不实施大改

对比：
A. 离线 FileAdapter（默认优先）；
B. 本地服务查询/执行 API（如已有稳定接口）；
C. 直接进程/插件/共享内核（仅证据支持时）。

从真实工程出发建议一个最小接口，包括：
- 模型/场景快照；
- System 目录；
- 运行与状态变更；
- trace/历史完备度；
- 能力声明；
- 稳定 ID/版本映射。

区分：现在**可读**、可以经过转换实现、只能显示黑盒、需要改原生内核、无法无损适配。

## 严格要求

- **只读审计**：不要修改两个工程的源文件、不要写生产数据库、不要触发生产推演、不要清理工作区、不要未经授权下载/上传任何业务数据。
